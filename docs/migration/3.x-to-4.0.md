# Heron 4.0 , no migration needed

Covers moving from `@heron-ws/app-runtime@3.x` through `4.0.4`. This release
(PR [#964](https://github.com/white-stork/heron/pull/964), hardened by later patches) switches every registry component bundle from a
standalone IIFE to an ESM module served through a host import map, and adds
several new build-time and dev-time checks.

**There is no code migration.** Nothing in this release renames or removes a
`$heron` method, a metadata field, or a contract key. The only thing you have
to do is clear out bundles built by the _old_ registry (IIFE format) and let
the app fetch fresh ones from the _new_ registry (ESM format) — see
[Step 3](#3-clear-cached-bundles-and-build-output).

## Is this migration required?

Installing `4.0.x` is required to pick up the ESM bridge, the new
validations, and the `asChild` host-adoption fix. Whether you need to _do_
anything beyond upgrading and rebuilding depends only on whether your app has
stale bundles on disk — see the compatibility note in
[Step 3](#3-clear-cached-bundles-and-build-output). Nothing here requires
touching `app.config.ts`, `app-manifest.json`, or any widget's
`metadata.json`.

## What's new

| Feature                                          | What it gives you                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IIFE bundles → ESM bundles                       | Registry components now resolve shared singletons (React, ReactDOM, component-registry, etc.) through a real ESM import map instead of a hand-maintained `window.__HERON_SHARED__` externals list. A dependency the list forgot used to mean a duplicate React instance and `Cannot read properties of null (reading 'useState')` at runtime — the import map makes that a resolution-time problem instead of a silent runtime one.     |
| Packaged/portable component styles               | Component styles now ship inside the component bundle instead of depending on a shared global stylesheet being present in the host app. See the `portable-styles-demo` dev widget.                                                                                                                                                                                                                                                      |
| HTML semantics validation                        | A dev-time DOM scanner (`window.__HERON_DOM_DIAGNOSTICS__`) flags real rendered-HTML violations — nested interactive elements, nested `<form>`/`<label>`, invalid `<p>` descendants, wrong table/list parent-child pairs — as they happen, with the offending widget name and a highlight you can pin.                                                                                                                                  |
| Composable component family placement validation | A build-time check resolves every route's fully composed tree (including section-references and layouts) and validates it against each component's contract: required ancestor, allowed direct children, "children required," max-instances-per-tree, and app-root-only lifetime. Catches a misplaced compound-component part (e.g. an `AccordionItem` outside an `Accordion`) at build time.                                           |
| Host adoption for `asChild`                      | Registry components can declare a host-adoption contract so Heron continues a Radix-style `Slot` merge _across_ Heron's own renderer boundary — events, `style`, and `className` from the adopting parent compose onto the single metadata child instead of both being rendered as separate elements. This is what fixes the shadcn **"button cannot appear as a descendant of button"** error for `<Button asChild>` used in metadata. |
| Prop schema registration                         | Fixes issue #941 ("prop schemas missing at runtime," resolved in [PR #964](https://github.com/white-stork/heron/pull/964)) — a component's prop schema (derived from `contract.json`) is now actually registered and available at runtime, not just at build time, so required-prop errors and defaults work correctly.                                                                                                                 |
| Explicit runtime deps / import-map integration   | The browser runtime resolves shared packages through an import map rather than a manually-curated externals list — see the ESM bundles row above.                                                                                                                                                                                                                                                                                       |

## Breaking changes to check

None. This release is additive and internal to the build/runtime pipeline.
The only compatibility concern is mechanical, not semantic — see the next
section.

## Step-by-step

### 1. Upgrade Heron

```bash
pnpm add \
  @heron-ws/app-runtime@^4.0.2 \
  @heron-ws/app-runtime-server@^3.0.0
```

If they are direct dependencies of your app, also bump:

- `@heron-ws/page-engine@^3.0.0`
- `@heron-ws/app-runtime-core@^2.0.2`
- `@heron-ws/page-engine-components@^2.0.2`
- `@heron-ws/app-runtime-native@^5.0.0` (React Native apps only)

`@heron-ws/component-api`, `@heron-ws/component-registry`, `@heron-ws/i18n`,
and `@heron-ws/utils` did not change in this release.

### 2. Rebuild the registry you consume from

The ESM bundle format is produced by `heron_registry` itself, so it must be
rebuilt with a current checkout before your app has anything new to fetch:

```bash
cd ../heron_registry
git pull --ff-only
pnpm install
pnpm --filter component-registry build:force
pnpm --filter component-registry start
```

`build:force` (not a plain `build`) matters here — the incremental build
cache does not treat "the output format changed" as a reason to rebuild an
otherwise-unchanged component, so a plain `build` immediately after pulling
can still serve stale IIFE output.

### 3. Clear cached bundles and build output

**Do not reach for `heron-clean-artifacts` / `pnpm clean:artifacts` for this**
— that script is an unrelated one-time migration for a much older on-disk
layout change and does not touch `bundles/`, `.bundle-lock.json`, or
`dist-app/`.

From the consumer app root, delete:

```bash
rm -rf bundles/ .bundle-lock.json dist-app/ dist-server/ dist/ build/
```

Why each one:

- **`bundles/`** — the vendored registry components your app fetched and
  cached on disk. These are still in the old IIFE format until removed.
- **`.bundle-lock.json`** — the ETag/freshness lock that decides whether a
  re-fetch is even attempted. It's **git-tracked**, so after regenerating it
  in the next step you'll want to commit the new version.
- **`dist-app/`, `dist-server/`, `dist/`, `build/`** — compiled widget
  scripts, the lifecycle bundle, and the SSR/Vite output. These were built
  against the old bundle graph and should be regenerated, not merged with new
  output.

`bundle-manifest.json` (the committed registry-endpoint config) and
`bundle-manifest.local.json` (your personal dev override, if any) are **not**
caches — leave both alone.

### 4. Rebuild the app

```bash
pnpm build
```

This re-vendors every component from the (now-ESM) registry into a fresh
`bundles/`, regenerates `.bundle-lock.json`, and rebuilds `dist-app/` /
`dist-server/`.

### 5. Native apps only

`@heron-ws/app-runtime-native` went `4.x → 5.0.0` in the same release. Rebuild
and republish your OTA bundle with the updated `heron-build-bundle` before
shipping — see the
[app-runtime-native changelog](https://github.com/white-stork/heron/blob/main/packages/app-runtime-native/CHANGELOG.md)
for the full OTA-signing context; it is unrelated to the ESM change but ships
in the same version bump.

## Verification checklist

- `pnpm build` passes end to end with no `Could not resolve` / externals
  errors.
- Browser console has no `Cannot read properties of null (reading 'useState')`
  or duplicate-React warnings on any page.
- In dev, `window.__HERON_DOM_DIAGNOSTICS__.state.status` is `"valid"` for
  your pages, or any reported violations are pre-existing markup issues, not
  new ones.
- Any `<Button asChild>` / Radix-style trigger authored in metadata renders
  exactly one interactive DOM element — no "button cannot appear as a
  descendant of button" console error.
- `git status` shows a regenerated `.bundle-lock.json` — commit it.

## Rollback

Revert the `@heron-ws/*` package versions, then repeat
[Step 3](#3-clear-cached-bundles-and-build-output) and rebuild — the ESM
bundles served by an upgraded registry won't run on the older runtime, so
rolling back the app without also clearing `bundles/`/`.bundle-lock.json`
leaves you with a mismatched cache either direction.
