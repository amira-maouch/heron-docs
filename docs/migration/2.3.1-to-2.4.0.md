# Migrating to the centralized `AuthAdapter` (`app-runtime@2.4.0`)

Covers what changes moving from `@heron-ws/app-runtime@2.3.x` to `2.4.0`.
This release centralizes authentication through the server `AuthAdapter`:
every Bearer or cookie credential is now verified by `AuthAdapter.verify()`
before permissions are loaded or a request is treated as authenticated — no
code path reaches `loadPermissions()` with an unverified token anymore.
Cookie sessions are now opt-in, so Bearer-only apps (no Heron cookie,
no `authenticate()`) are fully supported.

Most of this is additive and requires no changes. One path is removed
outright because keeping it would defeat the point of this release — see
[Breaking changes to check](#breaking-changes-to-check).

## Is this migration required?

Installing `2.4.0` is required to get any of its fixes/dependents. Whether
you need to *change* anything depends entirely on which authentication
pattern your app already uses — check the
[compatibility matrix](#compatibility-matrix) below. Most apps with a
working `AuthAdapter` today need zero code changes.

## What's new

| Feature                                    | What it gives you                                                                              | Guide                                                                                                          |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `auth: true` / `auth: false`                | A route/node/action boundary for "any verified user," independent of a specific `can` permission | [Authentication & Authorization](/docs/guides/backend-and-auth/authentication-and-authorization)                |
| Optional `AuthAdapter.loadPermissions()`    | Apps with no RBAC can implement only `verify()` — no need to write a permissions function you don't use | [`loadPermissions()` Examples](/docs/guides/backend-and-auth/auth-adapter/load-permissions-examples)           |
| `authorization.auth.session`                | Cookie sessions become opt-in; omit it entirely for Bearer-only apps (native clients, SPA-only auth) | [Authentication & Authorization](/docs/guides/backend-and-auth/authentication-and-authorization)                |
| Build-time adapter validation               | `pnpm build` now imports your configured adapter and fails the build if it's missing `verify()`, or declares `can` anywhere without `loadPermissions()` | — no app changes needed, just a build error instead of a production 403 |

## Breaking changes to check

| Area                                          | What changed                                                                 | What to check in your app                                                                                |
| ----------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `authorization.permissions.loader`/`.adapter` | **Removed.** This standalone pipeline let an app authorize `can` checks without ever routing the credential through `AuthAdapter.verify()` — exactly the gap this release closes. | If you use it: every protected `can`/route now fails closed (403/401) until you migrate — see [Step 2](#2-only-if-you-use-the-old-standalone-permissions-loader). If you already use an `AuthAdapter`: nothing to do. |
| `fetchClientPermissions()` (client)            | On a failed `/api/auth/permissions` request, this now throws instead of silently returning `[]`. `$egret.auth`'s store already catches it, so the resulting rule set is unchanged (`[]`) — but store `status` becomes `"error"` instead of `"ready"`. | Only matters if your UI branches on `$egret.auth` status specifically to distinguish "loaded, no rules" from "failed to load." Most apps render the same either way. |

Nothing else in this diff renames or removes an existing `$self`/`$egret`
method used by widget scripts.

## Compatibility matrix

| Your current setup                                                        | After upgrading to `2.4.0`                                                    |
| ----------------------------------------------------------------------------| --------------------------------------------------------------------------------- |
| `AuthAdapter` with `verify`, `loadPermissions`, `authenticate`, `revoke`   | Works unchanged.                                                               |
| `AuthAdapter` with only `verify` (no RBAC)                                 | Works unchanged — `loadPermissions` was already effectively unused.            |
| `authorization.auth.cookie` (old top-level key)                            | Still works — read as a deprecated fallback for `auth.session.cookie`, with a `console.warn`. Move it when convenient, not urgent. |
| No `cookie`/`session` config at all, relying on implicit cookie defaults   | **Changed.** Cookie sessions are now opt-in. If your app calls `POST /api/auth/session` and never configured `cookie` explicitly, add an explicit `auth.session.cookie` block — see [Step 3](#3-only-if-you-relied-on-implicit-cookie-defaults). |
| `authorization.permissions.loader`/`.adapter` (no `AuthAdapter`)          | **Breaks.** See [Step 2](#2-only-if-you-use-the-old-standalone-permissions-loader). |
| No `authorization` config at all                                          | Unaffected.                                                                     |

## Step-by-step

### 1. Install `2.4.0`

```bash
pnpm add @heron-ws/app-runtime@^2.4.0 @heron-ws/component-api@^5.1.0 @heron-ws/page-engine@^1.4.0
```

Then rebuild (`pnpm build:app` or your usual build command). If your
configured adapter is missing `verify()`, or declares `can` somewhere in
`app-manifest.json`/widget metadata without implementing `loadPermissions()`,
the build now fails with a clear message instead of surfacing as a
production 401/403. If your build passes, skip straight to
[Verification checklist](#verification-checklist) unless one of the next two
steps applies to you.

### 2. Only if you use the old standalone permissions loader

If `app.config.ts` has (or had, before this repo's own migration)
`authorization.permissions.loader`/`authorization.permissions.adapter` and
no `authorization.auth.adapter`, that path is gone. Move the same logic into
an `AuthAdapter`:

```ts
// Before — authorization.permissions.loader + .adapter, no AuthAdapter
export async function loadPermissions(token: string | null) {
  return fetchFromBackend(token);
}
export function adaptPermissions(raw: unknown) {
  return mapToRules(raw);
}
```

```ts
// After — authorization/auth-adapter.ts
import type { AuthAdapter } from "@heron-ws/app-runtime";

const adapter: AuthAdapter = {
  async verify(credential) {
    // Whatever you used to trust implicitly on the Bearer token — verify it
    // here instead. Return null for an expired/invalid/malformed credential.
    const user = await backendVerify(credential);
    if (!user) return null;
    return { credential, principal: toPrincipal(user), expiresAt: user.expiresAt };
  },
  async loadPermissions(identity) {
    return mapToRules(await fetchFromBackend(identity.credential));
  },
};
export default adapter;
```

```ts
// app.config.ts
authorization: {
  enabled: true,
  auth: { adapter: "./authorization/auth-adapter.ts" }, // no `permissions` block anymore
},
```

The key behavior change: your old loader trusted the raw Bearer token and
handed it straight to the backend for a permissions lookup, with nothing
verifying it was a real, live credential first. `verify()` is that missing
check — put whatever validated "is this credential real" logic you have
(or add one) there, and only call your permissions backend from
`loadPermissions()` once `verify()` has already vouched for the identity. If
you have no such check today, this is the actual gap this release exists to
close, and there is no config-level way to skip it.

### 3. Only if you relied on implicit cookie defaults

Before `2.4.0`, configuring `auth.adapter` alone unconditionally created an
HttpOnly cookie policy using built-in defaults (`heron_auth`, 30 minutes,
`lax`, secure-auto), even if you never wrote a `cookie` block. If your app
calls `POST /api/auth/session` / `GET /api/auth/session` and never configured
`cookie` explicitly, add:

```ts
authorization: {
  enabled: true,
  auth: {
    adapter: "./authorization/auth-adapter.ts",
    session: { cookie: {} }, // empty is fine — same defaults as before
  },
},
```

If your app is Bearer-only and never calls those endpoints, no action is
needed — the new default (no cookie) is what you already behaviorally had.

### 4. Optional: adopt `auth: true` boundaries

If your app currently protects a "must be logged in, no specific permission"
route with a `can: { action: "*", subject: "*" }` wildcard (an
administrator-level check being misused as "logged in"), replace it:

```diff
- "dashboard": { "widget": "pages/dashboard", "can": { "action": "*", "subject": "*" } }
+ "dashboard": { "widget": "pages/dashboard", "auth": true }
```

This is optional and has no deadline — existing `can` declarations keep
working exactly as before.

### 5. Optional: drop unused `loadPermissions`

If your `AuthAdapter` implements `loadPermissions` but your app has no `can`
declarations anywhere, you can delete it — `verify()` alone is enough for
`auth: true`/`auth: false`. Not required; an unused `loadPermissions` that
always returns `[]` is harmless.

## Verification checklist

- `pnpm build` passes (or fails with a specific, actionable adapter-shape
  error — not a generic runtime crash).
- A protected route with no credential returns `401`, not `403` or a silent
  render.
- A verified user without the required `can` rule returns `403`.
- If you use Heron session cookies: login/logout via
  `POST`/`DELETE /api/auth/session` still round-trips a working cookie.
- If you're Bearer-only: confirm no `Set-Cookie` header appears on any
  `/api/*` response.
- `GET /api/auth/permissions` returns `200` with rules for a verified user
  and `401` for an unverified one (previously some setups returned `200`
  with `[]` for unverified — this is the one visible status-code change for
  that endpoint).

## Rollback

Revert the three `@heron-ws/*` package versions. Nothing in `2.4.0` changes
on-disk config formats destructively — `auth.cookie` and `auth.session.cookie`
are both still valid keys — so rolling back does not require touching
`app.config.ts`. The one exception is if you completed
[Step 2](#2-only-if-you-use-the-old-standalone-permissions-loader): keep both
the new `AuthAdapter` and the old `permissions.loader`/`.adapter` config
around until you're confident you won't roll back, since `2.3.x` doesn't know
about the new adapter shape.
