# Migrate from Heron 5.0.0 to 5.1.1

Heron 5.1.1 secures registry downloads in two ways:

- the registry requires a preallocated consumer token; and
- the app verifies every published release with the registry's public signing
  key before accepting its files.

This migration applies to web consumer applications. Use these package
versions together:

| Package | Required version |
| --- | --- |
| `@heron-ws/app-runtime` | `5.1.1` |
| `@heron-ws/app-runtime-server` | `4.1.2` |
| `@heron-ws/component-api` | `6.1.0` |

`app-runtime-server@4.1.2` is important even when it is only a transitive
dependency: it contains the installer support needed for the current signed
registry releases.

## Before you start: the two tokens are different

Do not confuse package-install authentication with registry-download
authentication:

| Variable | Used for | Required during |
| --- | --- | --- |
| `NODE_AUTH_TOKEN` | Installing private `@heron-ws/*` packages from GitHub Packages | `pnpm install` |
| `HERON_REGISTRY_TOKEN` | Downloading component, widget, and plugin artifacts from the Heron registry | `heron-build-components` / `heron-build-app` / any build that invokes them |

Registry tokens are preallocated by the registry administrator for each
consumer application. Application teams must use the token assigned to their
app; they must not generate a replacement or reuse another application's
token.

Never commit either token to `package.json`, `bundle-manifest.json`, an Actions
workflow, or a tracked `.env` file. The public release-verification key is safe
to commit; the tokens and private signing key are not.

## 1. Upgrade the packages

Update `package.json` so it contains the following versions. Pinning
`app-runtime-server` with a pnpm override also updates the copy brought in by
`app-runtime`:

```json
{
  "dependencies": {
    "@heron-ws/app-runtime": "5.1.1",
    "@heron-ws/component-api": "6.1.0"
  },
  "pnpm": {
    "overrides": {
      "@heron-ws/app-runtime-server": "4.1.2"
    }
  }
}
```

If the application already declares `@heron-ws/app-runtime-server` directly,
pin that dependency to `4.1.2` too. Preserve any existing pnpm overrides.

Install the updated dependencies:

```bash
pnpm install
```

`NODE_AUTH_TOKEN` must be available to pnpm if the packages are installed from
the private GitHub Packages registry.

## 2. Trust the registry's public release key

Keep the production registry URLs under `registries` and add
`trustedReleaseKeys` to `bundle-manifest.json`:

```json
{
  "registries": {
    "ui": "https://registry.heron.ws/api/registries/ui",
    "shadcn": "https://registry.heron.ws/api/registries/shadcn",
    "egret-ui": "https://registry.heron.ws/api/registries/egret-ui"
  },
  "trustedReleaseKeys": [
    {
      "keyId": "registry-release-2026",
      "publicKey": "MCowBQYDK2VwAyEA9ZAe7tQchbaF4v4FlLoiasoUBjBOX+UCBwZqBjlVZjs=",
      "registries": ["ui", "shadcn", "egret-ui"]
    }
  ]
}
```

The `registries` array on the key must list every registry ID used by that
application and only those registry IDs. For example, add `skip`, `alefbab`, or
another app-specific registry when it appears in the same manifest.

This is an Ed25519 **public** key. It verifies releases but cannot sign them,
so it belongs in source control.

## 3. Configure the preallocated registry token locally

Store the assigned token in the machine's password manager or credential
store, then expose it to the shell that runs Heron:

```bash
export HERON_REGISTRY_TOKEN='<the preallocated token for this app>'
```

The variable is read only during the build and is sent to the registry as the
registry credential. Heron does not write it to `.bundle-lock.json`, vendored
artifacts, or browser output.

An `.env.local` file is not sufficient unless the application's command
explicitly loads that file **before** `heron-build-components` starts. Check
the environment in the same terminal instead:

```bash
test -n "$HERON_REGISTRY_TOKEN" && echo "registry token is available"
```

Do not print the token itself.

## 4. Add the token to the deployment build

Create a GitHub Actions repository secret named `HERON_REGISTRY_TOKEN` and set
it to that application's preallocated token:

1. Open the consumer repository in GitHub.
2. Go to **Settings → Secrets and variables → Actions**.
3. Create the repository secret `HERON_REGISTRY_TOKEN`.

Then expose the secret only to the build step in
`.github/workflows/deploy.yml`:

```yaml
- name: Build
  env:
    HERON_REGISTRY_TOKEN: ${{ secrets.HERON_REGISTRY_TOKEN }}
  run: pnpm build
```

If the workflow invokes `pnpm heron-build-components`, `pnpm build:app`, or
another wrapper instead, put the same `env` block on the step that invokes it.
Setting the secret on the install step alone will not make it available to a
later build step.

Keep `NODE_AUTH_TOKEN` on the dependency-install step when it is needed:

```yaml
- name: Install dependencies
  env:
    NODE_AUTH_TOKEN: ${{ secrets.NODE_AUTH_TOKEN }}
  run: pnpm install --frozen-lockfile
```

`NODE_AUTH_TOKEN` cannot replace `HERON_REGISTRY_TOKEN`.

## 5. Resolve and verify the current signed releases

To deliberately resolve the newest versions allowed by
`bundle-manifest.json`, refresh the component lock:

```bash
pnpm heron-build-components --update
pnpm dev
```

Review and commit the regenerated `.bundle-lock.json` with the migration. A
plain `pnpm heron-build-components` honors the existing lock and therefore may
keep an older matching release; this is intentional reproducible-build
behavior.

CI should use the committed lock without changing it. Where the workflow runs
the component builder directly, use:

```bash
pnpm heron-build-components --frozen-lockfile
```

When the app talks to the hosted registry, always use the normal strict
command:

```bash
pnpm dev
```

Strict mode requires HTTPS and valid signatures. Do not enable the development
escape hatches for a hosted, CI, staging, or production build.

## Developing against the local registry on port 4100

Local component work has not passed through the deployment signing pipeline,
so its new releases are unsigned. Redirect registry requests locally without
editing the committed production manifest by creating the gitignored
`bundle-manifest.local.json`:

```json
{
  "registries": {
    "*": "http://localhost:4100"
  }
}
```

The `*` base maps every registry already declared in `bundle-manifest.json` to
`http://localhost:4100/api/registries/<registry-id>`. Ensure
`bundle-manifest.local.json` is listed in `.gitignore`.

Add this development-only script to `package.json` if it is not already
present:

```json
{
  "scripts": {
    "dev:insecure": "HERON_ALLOW_UNSIGNED_COMPONENTS=1 HERON_ALLOW_INSECURE_REGISTRIES=1 pnpm dev"
  }
}
```

With the local registry running on port 4100, use:

```bash
pnpm dev:insecure
```

The two flags have narrow purposes:

- `HERON_ALLOW_UNSIGNED_COMPONENTS=1` permits unsigned local releases.
- `HERON_ALLOW_INSECURE_REGISTRIES=1` permits HTTP only for `localhost` or
  `127.0.0.1`.

They do not bypass registry authentication. If authentication is enabled on
the local registry, its token must still be present in
`HERON_REGISTRY_TOKEN`. A local registry started with authentication disabled
does not need one.

Before switching back to the hosted registry, remove or rename
`bundle-manifest.local.json`; otherwise the local override remains active.
Then run `pnpm dev`, not `pnpm dev:insecure`.

## Publishing changed components

Component release versions are immutable. When a component changes, bump the
version in its `contract.json` according to SemVer and push the change through
the normal registry pull-request process.

After the change reaches `main`, the registry deployment pipeline builds the
release and signs it automatically using the private Ed25519 signing key held
by CI. Developers do not have that private key and therefore cannot sign a
release locally. This separation is intentional:

- the private key exists only in the registry publication pipeline;
- consumer applications contain only the public key; and
- local development uses unsigned releases with `pnpm dev:insecure`.

Do not copy the private signing key to a developer machine or consumer
repository. If a hosted release is reported as unsigned, fix or rerun the
registry publication pipeline; do not weaken signature verification in the
consumer app.

## Verification checklist

- [ ] `@heron-ws/app-runtime` is exactly `5.1.1`.
- [ ] every resolved copy of `@heron-ws/app-runtime-server` is `4.1.2`.
- [ ] `@heron-ws/component-api` is exactly `6.1.0`.
- [ ] `pnpm install` succeeds with `NODE_AUTH_TOKEN` where required.
- [ ] `bundle-manifest.json` contains the public key and all registry IDs used
      by the app.
- [ ] the assigned `HERON_REGISTRY_TOKEN` is available locally but is not
      committed.
- [ ] the Actions repository contains the `HERON_REGISTRY_TOKEN` secret and
      the build step receives it.
- [ ] `pnpm heron-build-components --update` succeeds against the hosted
      registry and regenerates `.bundle-lock.json`.
- [ ] `pnpm dev` succeeds against the hosted signed registry.
- [ ] `pnpm dev:insecure` succeeds against the unsigned local registry on port
      4100.
- [ ] no CI, staging, or production command sets either insecure-development
      flag.

## Common failures

| Error | Cause and fix |
| --- | --- |
| Registry request returns `401` or `403` | `HERON_REGISTRY_TOKEN` is absent, incorrect, revoked, or allocated to another consumer. Verify the build-step environment and ask the registry administrator to confirm the assignment. |
| Release is signed by an untrusted key | `trustedReleaseKeys` is missing the key or does not list the affected registry ID. Update `bundle-manifest.json`; never bypass this in a hosted build. |
| Release is unsigned | Use `pnpm dev:insecure` only for a local unsigned registry. For the hosted registry, repair the signing/deployment pipeline. |
| HTTP registry is rejected | Use HTTPS for hosted registries. For `localhost:4100`, use `pnpm dev:insecure`. |
| A newly published version is not selected | The lock is authoritative. Run `pnpm heron-build-components --update`, review the new lock, and commit it. |
| No published release satisfies a version | Publish the component version first, verify the registry deployment completed, then update the consumer lock. |
