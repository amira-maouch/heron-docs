# Adding SEO to Pages

SEO metadata resolves from four sources, each overriding the one before it,
then gets written into `<head>` at render time. `canonical` and `robots` are
the one exception — they're capped at the **Static** layer no matter what, so
request-derived data can never make protected content indexable.

| Source | Where it comes from | Priority |
|---|---|---|
| Autogenerated | Page title fallback; `robots.txt`/`sitemap.xml` generation | Lowest |
| Static | `app-manifest.json` — app-level `seo`, then route-level `seo` | Low |
| Dynamic | Read automatically off an entity your loader returns as `seoSource` | Medium |
| Custom | An explicit `seo` object your loader returns directly | Highest (except `canonical`/`robots`) |

## Autogenerated

If nothing else sets a title, the resolved page title is used as-is —
no config needed. `robots.txt`/`sitemap.xml` are generated from your manifest
automatically too; see below.

## Static — `app-manifest.json`

```json
{
  "title": "My App",
  "seo": { "description": "Default description", "robots": "index, follow" },
  "routes": {
    "products/:id": {
      "widget": "pages/product",
      "title": "Product",
      "seo": {
        "canonical": "/products",
        "openGraph": { "type": "product" }
      }
    }
  }
}
```

Title/description/image set anywhere also get auto-mirrored into Open Graph
and Twitter tags, and `hreflang` alternates get generated for every supported
locale automatically.

## Dynamic — derived from a `seoSource` entity

Return your data under a `seoSource` key and Heron reads SEO fields off it by
naming convention — no manual mapping:

```ts
// widgets/pages/product/server.ts
export async function loader(ctx: ServerContext) {
  const product = await fetchProduct(ctx.params.id);
  return { product, seoSource: product };
}
```

Convention (first match wins per field):

| SEO field | Read from, in order |
|---|---|
| `title` | `.title` → `.name` → `.code` |
| `description` | `.description` → `.summary` → `.excerpt` |
| `image` | `.image` → `.coverImage` → `.thumbnail` |
| `index: false` | `.isPublic === false` → `.status === "draft"` → `.visibility === "private"` |

If `product` has a `name` and `summary` field, for instance, those become the
page's title and description with zero extra code — useful when your
entities already follow common naming, and you don't want to hand-write an
`seo` object for every content type.

## Custom — explicit `seo` from a loader

For full control (or when your entity doesn't match the `seoSource`
convention), return an `seo` object directly instead:

```ts
// widgets/pages/product/server.ts
export async function loader(ctx: ServerContext) {
  const product = await fetchProduct(ctx.params.id);
  return {
    product,
    seo: {
      title: product.name,
      description: product.shortDescription,
      image: product.heroImageUrl,
    },
  };
}
```

This wins over both the Dynamic and Static layers for the fields it sets
(again, except `canonical`/`robots`, which never come from a loader).

## robots.txt and sitemap.xml

Generated automatically from your manifest — a route is excluded from the
sitemap if it has a `can` declaration (authenticated) or sets
`"seo": { "index": false }`. Non-production environments always serve
`Disallow: /` in `robots.txt`, so staging never gets indexed by accident.

## What's not confirmed yet

No structured data / JSON-LD (`application/ld+json`) generation exists in the
code as of this writing. Per-key **translated** SEO strings (so a page's
title/description differ by locale automatically) aren't wired into the SEO
resolver yet either, as far as could be verified against the current SSR
branch — the underlying per-request locale/translation infrastructure exists,
it just isn't connected to this path. If you need locale-specific SEO text
today, derive it yourself in the loader (e.g. read the locale from wherever
your app already tracks it, and pick a title/description manually) rather
than assuming a `t:`-style key works here — it doesn't yet.

## Verifying it

```bash
curl -sS http://localhost:5173/products/123 | grep -E '<title>|<meta|rel="canonical"'
```
